# Разбор неуспешных учений РЦОД: consent-registry, 11.11.2026

Формат без поиска виноватых: ищем, что в процессе позволило ошибке случиться. Данные вымышленные.

## Что произошло

Плановые учения по переключению consent-registry из основного ЦОД в резервный. Цель RTO 15 минут, получилось 27. Учения не пройдены.

## Хронология

| Время | Что происходило |
|---|---|
| 10:00 | Старт учений, трафик основного ЦОД для сервиса отключён |
| 10:02 | Поды в РЦОД поднялись, проверка готовности не проходит |
| 10:05 | База данных уже переключена на РЦОД, сервис продолжает стучаться в основной ЦОД |
| 10:09 | Причина найдена: адрес базы прописан в конфигурации сервиса явно |
| 10:21 | Конфигурация исправлена вручную, сервис перезапущен |
| 10:27 | Проверки проходят, сервис отвечает. RTO 27 минут |

## Почему так вышло

1. Адрес базы задан в конфигурации явно, а не через имя, которое переключается вместе с базой.
2. В runbook есть шаг переключения базы, но нет шага проверки конфигурации сервиса после него.
3. Сервис вышел в прод 13.11 с теми же настройками. Готовность РЦОД не входила в чек-лист выхода, поэтому неуспешные учения выход не остановили и в трекере это было видно только на листе «РЦОД».

## Что сработало

- Мониторинг сразу показал, что проверка готовности не проходит: на поиск причины ушло 7 минут.
- Основной ЦОД держали готовым, откат не понадобился.

## Что делаем

| Действие | Ответственный | Срок |
|---|---|---|
| Перевести адрес базы на имя, которое переключается вместе с базой | Команда Идентификации | 25.11 |
| Добавить в runbook проверку конфигурации после переключения базы | Команда Идентификации | 25.11 |
| Повторить учения | Платформа DropApp, команда Идентификации | 27.11 |
| Добавить «РЦОД готов» в чек-лист выхода в прод для всех сервисов | Delivery Lead | сделано 18.11 |
| Проверить, нет ли явного адреса базы у других сервисов, которые идут в РЦОД | РГ всех команд | 02.12 |
